# 决策记录

## 立项：六个决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | 独立仓库，不并入其他项目 | 本服务是跨多条业务线的基础设施，App Secret 的爆炸半径应该只属于它自己，不与其他项目耦合 |
| 2 | 事件处理写成纯函数，WS 与 HTTP 两个入口都调它；默认长连接 | 长连接不开入站口、不动反向代理；webhook 作退路（服务器已有备案域名与现成的反向代理配置），切换只翻配置 |
| 3 | SQLite via `node:sqlite`（Node 24 内置） | 幂等靠 UNIQUE 原子保证、映射表要查询。不用 better-sqlite3 是因为它要拉预编译二进制，slim 镜像没编译器，构建期不可靠 |
| 4 | 附件落 `files/YYYY/MM/<message_id>/`，三道配额 | 同机还跑着别的服务（比如数据库），磁盘绝不能被写满。附件是证据，里程碑 1 不自动删 |
| 5 | Docker compose + `restart: unless-stopped` + 日志封顶 | 机器已有 Docker；不往生产宿主装 Node。json-file 默认无上限，长期跑下去会写满磁盘 |
| 6 | 三层健康：SDK 钩子 → 看门狗 → 对账轮询 | 「连着但收不到」只有端到端比对能发现；对账同时兜住断线期丢的事件，并能识别有人在别处抢事件 |

## 事件订阅归本服务独占

一个飞书应用的事件订阅**只能二选一**（长连接 或 一个 webhook 地址），长连接还会在多个消费者之间分流。
因此本服务从设计之初就独占这个应用的事件订阅；如果同一飞书应用还需要给其他系统转发事件，
应该在本服务内部按来源做二次分发（HTTPS POST 给下游），而不是让多个消费者同时订阅同一个应用的事件。

## 为什么不用现成项目

上线前调研过 GitHub 与飞书官方能力，结论是**自建正确**。存档理由，免得日后重问。

搜到的东西分三类，没一类对得上：

| 类别 | 例子 | 为什么不行 |
|---|---|---|
| 单向 webhook 群通知 | 各种「告警转飞书群」工具 | 是通知不是会话，没有回传路由 |
| 飞书 ↔ AI 编码助手桥接 | `m1heng/clawdbot-feishu`(4.2k)、`chenhg5/cc-connect`(15.6k) 等 | 会话路由做得不错，**但路由目标是有文件系统权限的编码智能体**——正是本项目要规避的提示注入面，方向相反 |
| 通用客服台 | `chatwoot/chatwoot`(37k) | 渠道列表里**没有飞书**，要自己写适配器（活一点没少），还得背 Postgres+Redis+Sidekiq+Rails，1.6GB 机器吃不消 |

**飞书官方服务台（Helpdesk）**两个硬伤：免费版不支持（商业版起），且交互模型是「每张工单拉一个群」，
不是「老师在自己与机器人的私聊里回一张卡片」。对「一位老师 + 零散学生提问」这种场景是杀鸡用牛刀还要花钱。

反向佐证：Telegram 生态里「reply 即回传给原发送者」的 feedback bot 有一堆独立实现，都是
「一张 message_id → user_id 映射表 + 判断是不是 reply」，没有 Redis 没有队列。说明本项目
「零运行时依赖、一张 routes 表」不是偷懒，是这类问题的常规解。

### 从调研里吸收的两条

1. **附件摘要必须流式算**。`clawdbot-feishu` 给入站媒体设体积上限的做法提醒了这一点——
   我们原来 `readFile` 整份进内存，容器只有 256MB，100MB 附件会撑爆。已改 `createReadStream` + `pipeline`。
2. **长连接的「存活」判断不要挂在业务事件上**。`clawdbot-feishu` issue #384 记录过：
   心跳 pong 没刷新 health monitor 的 `lastEventAt`，约 35 分钟后误判失活、触发无谓重连。
   本项目**没有这个问题**：看门狗只看 SDK 的连接态与对账失败次数，`last_event_at` 只用于展示。
   **以后谁都不要把 `last_event_at` 加进判死条件**——安静一整天不代表连接坏了。

值得以后做的（非刚需）：老师回复后把那张转发卡片的状态改成「已回复」，避免重复处理同一条。
